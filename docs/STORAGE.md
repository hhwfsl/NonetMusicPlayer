# 桌面数据存储

适用于 0.3.0-beta.5。桌面主状态使用 SQLite，数据库为 `Data/library.db`；配置、插件清单、布局以及独立 CLI 的状态继续使用 System.Text.Json Source Generation。

## 选择依据

Source Generation 能减少 JSON 类型反射与序列化开销，但不能消除整个文档的重写：即使只改变播放位置，完整 `state.json` 仍需序列化全部歌曲、歌单和统计。SQLite 可以在事务中更新变化的记录，而不重写整个文档；这些能力在 [SQLite 应用文件格式说明](https://www.sqlite.org/appfileformat.html)中有详细解释。

本项目的歌曲、歌单、按日歌曲统计分别存储为实体行，小型状态记录保存设置、最近播放和播放位置。采用主键 `(kind,id)`、WAL 和 `synchronous=FULL`。实体载荷仍使用源生成 JSON，便于继续使用已有类型和备份格式。普通业务保存比较实体变更；每 15 秒的播放状态保存只检查状态和统计，不扫描整张歌曲/歌单集合。

这不是“数据库在所有场景必然更快”。小型设置文件适合 JSON；当前界面的搜索、分类和统计仍主要使用内存模型，启动仍读取全部实体，尚未实现按需 SQL 查询或十万首规模承诺。SQLite 会增加少量原生依赖，不能直接降低所有 UI 内存。

本机隔离测试使用 10,000 首元数据、12 次播放位置更新，对照源生成 JSON 的完整快照与原子替换。一次测量为 SQLite 163.5 ms、JSON 198.7 ms；每次有效位置保存只改变一行。结果受文件系统缓存与磁盘影响，不能当作所有设备的性能保证；主要收益是有界的写入范围、事务一致性及后续扩展空间。可重新运行：

```powershell
dotnet run --project tests/NonetMusicPlayer.UiChecks.Desktop -- artifacts/storage-test --desktop-revision-only
```

每次测试的 `storage-benchmark.txt` 位于生成的独立 revision 目录中。

## 迁移与恢复

- 第一次读取旧 `state.json` 后，保存时写入 SQLite；旧 JSON 和原始媒体保留，不覆盖旧迁移来源。
- 主数据库损坏时尝试一致性备份，再尝试旧 JSON；损坏主库及侧文件归档，不就地覆盖。界面提示恢复结果。
- 默认在 `Backups/library.db.bak` 保留通过 SQLite 在线备份 API 生成的一致快照，滚动快照间隔约五分钟；它不是“每一次操作”的副本。操作撤销与明确恢复前的快照另行保留。
- 恢复支持有效 `.db` / `.bak` 和旧 `.json`；先验证，归档当前状态，再恢复，不自动播放，不修改备份源文件。
- 移动运行中的数据目录时，后续保存继续同步至待启用目录；原数据保留。不要只在播放期间复制裸 `.db` 而遗漏 WAL，优先退出后备份整个 Data，或使用一致性备份。
- CLI 使用独立 `cli-state.json`，拒绝打开含桌面 JSON 或 SQLite 主库的目录。

## 歌曲引用边界

“浏览歌曲”是全部歌单引用的集合。最近播放仅是历史；专辑、艺术家仅是分类，不提供删除歌曲或分类的操作。最后一个歌单引用被移除后，活动歌曲记录、对应历史/统计及应用生成的歌词/封面数据会回收；显式浏览删除会移除全部歌单引用并要求确认。

原始音频、相邻歌词和手动选择的源歌词不删除。移除生成文件时会保留可撤销的恢复归档，位于 Backups/RemovedTrackData；它们不再属于活动曲库。清理失败会通知用户，不误称原文件已删除。
